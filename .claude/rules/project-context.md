## Conventions

- **Language**: all display names, variables, log messages in Spanish (e.g. `ConfiguracionRobot`, `dtFacturaProcesada`, `"Leyendo assets"`)
- **File naming**: PascalCase, spaces allowed (`Procesar XML.xaml`)
- **Variable naming**: Hungarian-ish prefixes — `dt*` for DataTable, `arr*` for arrays/DataRow[], `list*`/`List*` for lists, `concat*` for accumulated strings
- **Config pattern**: single `l:Configuracion` object (from `LibCartaInstrucciones`) built once in Main.xaml from an Orchestrator asset path + `Configuración.xlsx`, then passed by reference into every child workflow — no hardcoded business paths inside `Procesar XML.xaml`/`LlenarCartaInstrucciones.xaml` (all `ConfiguracionRobot.Ruta*`)
- **Error handling**: `TryCatch` + `ui:LogMessage Level="Error"` + `Throw New Exception(msg, innerException)` is the dominant pattern — but **not applied consistently** (see Known Issues)
- **Dead code convention**: disabled logic is left in place wrapped in `ui:CommentOut` rather than deleted (used repeatedly across all 3 non-empty workflows)

## Architecture

- **Pattern**: Main orchestrates a single child workflow (Procesar XML); a second child workflow (LlenarCartaInstrucciones) and a zip-compression step exist but are switched off
- **Data flow**: `Entradas/*.xml` (CFDI + ComercioExterior) → join per line item against `Catálogo Tipos Producto.xlsx` (Tipo) and CAM catalog folder (Origen) on `NoIdentificacion` → aggregate per invoice → append row to `Prellenado.xlsx` (staging, consumed by the separate `GenerarCartaInstrucciones` robot) + write `Factura.xlsx` / `Origen Facturas.xlsx`
- **Execution flow**: Main → GetRobotAsset(`DIL-CIConfiguracion`) → read `Configuración.xlsx` → build `Configuracion` → copy templates → Invoke `Procesar XML.xaml` → **end** (disabled: invoke LlenarCartaInstrucciones → zip outputs)
- **External integrations**: none beyond local filesystem/Excel; no HTTP/DB/mail/UI-automation activity observed despite those packages being referenced

## Known Issues / Observations (facts, not recommendations)

- **`UsarCatalogoUSA` has no effect on behavior**: `Procesar XML.xaml` branches on this flag (`If_13`), but both `If.Then` and `If.Else` read the **same** folder, `ConfiguracionRobot.RutaCatalogoCAM` — the `RutaCatalogoUSA` config value (present in `Configuracion` and in `Configuración.xlsx`) is read at startup but **never referenced** anywhere in any workflow
- **`LlenarCartaInstrucciones.xaml` is fully implemented but disabled**: its `InvokeWorkflowFile` call in Main.xaml is wrapped in `ui:CommentOut`. It duplicates carta-generation logic that, per current business description, now lives in a separate "GenerarCartaInstrucciones" robot — two implementations of the same responsibility exist in the codebase
- **`DividirFacturas.xaml` is an empty, unreferenced scaffold** (root `Sequence` has no children) — dead file
- **Inconsistent error handling on catalog reads**: reading `Catálogo Tipos Producto.xlsx` (TryCatch_1) rethrows on failure; reading the CAM catalog (TryCatch_2, `catch` at line ~376) only logs `Level="Error"` and **swallows the exception** — the file continues processing with whatever `dtCatalogoOrigen` state existed before the failed read (could be silently empty/stale for the whole run)
- **Hardcoded dev-machine absolute paths** remain in `Procesar XML.xaml` inside three `ui:CommentOut` blocks (`C:\Users\PC\Documents\Devol\Diltex\Origen\Salidas\Origen Facturas.xlsx`), and in Main.xaml's disabled `ForEachFileX`/`CompressFiles` blocks — all currently inert (commented out) but not using `ConfiguracionRobot.*`
- **Stale log message**: the CAM-catalog error log references a specific hardcoded filename (`"Catálogo CAM I21, P22, V22, O22 & I22.xlsx"`) even though the actual read now iterates every file in the folder via `ForEachFileX`
- **Unused variable `cc`**: assigned `"http://www.sat.gob.mx/ComercioExterior11"` (namespace v1.1, not v2.0) per invoice but never read — the actual `cfdi` namespace used for parsing comes from `xml.Root.GetNamespaceOfPrefix("cfdi")` instead; the ComercioExterior complement's own namespace is not used anywhere — origin is determined purely by catalog lookup on `NoIdentificacion`, not by reading complement fields directly
